# 测试执行 Playbook

## 目标

执行功能模块或项目的测试流程，收集结果、识别失败级别，并生成可复用的测试报告。

这个 playbook 保留原 `/run-tests` 的核心能力：
- 定位测试文件
- 调用测试框架执行测试
- 统计通过、失败、跳过与覆盖率
- 生成测试报告
- 根据严重程度给出后续动作

## 输入

- 功能名称或模块名称：必填，除非明确执行全量测试
- 测试范围：可选，例如单模块、全量
- 测试框架：可选，默认按项目配置检测
- 是否生成测试模板：可选

## 输出

至少产出：
- 测试执行摘要
- 失败用例详情
- 覆盖率信息（如项目支持）
- 测试报告文档

默认建议输出到：
- `docs/{feature}/40_TEST_REPORT.md`

## 依赖

- 参考命令：`.codex/commands/run-tests.md`
- 相关 playbooks：`new-feature`、`check-gate`
- 后续能力：`test-plan-writer`、`test-report-generator`

## 执行步骤

### 1. 校验输入

1. 功能名为空时，要求用户指定功能或明确全量测试。
2. 如果指定的是模块测试，优先查找与该功能相关的测试文件。
3. 如果项目不存在任何测试框架配置，应明确说明当前无法自动执行。

### 2. 定位测试文件

优先查找：
- `src/**/{feature}/**/*.spec.*`
- `src/**/{feature}/**/*.test.*`
- `tests/{feature}/**/*.spec.*`
- `tests/{feature}/**/*.test.*`

如果没有找到测试文件：
- 不要伪造执行结果
- 明确提示未找到测试
- 如适合，可建议生成测试模板

### 3. 检测并执行测试框架

优先识别：
- Vitest
- Jest
- 项目自定义 `npm run test` / `pnpm test` / `yarn test`

执行时应尽量保留：
- 测试命令
- 运行范围
- 执行时长
- 原始失败线索

### 4. 收集测试结果

至少收集：
- 总测试数
- 通过数
- 失败数
- 跳过数
- 执行耗时
- 覆盖率（如可得）
- 失败测试详情

### 5. 生成测试报告

建议报告结构：
- 测试概览
- 覆盖率
- 测试详情
- 失败分析
- 改进建议

文档要求：
- 主要内容使用中文
- `Vitest`、`Jest`、`coverage`、`stack trace` 等术语可保留英文
- 失败信息要以帮助修复为目标，而不是只贴原始日志

### 6. 失败分级与处理策略

建议沿用原框架的严重度概念：
- `P0`：功能完全不可用，立即修复
- `P1`：核心流程受阻，立即修复
- `P2`：可绕过问题，记录后续修复
- `P3`：体验问题，记录优化

要求：
- `P0` / `P1` 应视为阻塞型失败
- `P2` / `P3` 可记录后继续
- 报告中要区分不同级别问题

### 7. 可选生成测试模板

当未找到测试且用户希望快速建立基线时，可生成测试模板。

模板要求：
- 可直接运行
- 至少覆盖初始化、正常输入、边界输入、错误处理
- 保留明显 TODO 提示，避免伪完整测试

## 核心原则

1. 没有执行就不要声称测试通过。
2. 报告要对修复有帮助，而不是只做统计展示。
3. 失败分级要服务于决策节奏。
4. 覆盖率是参考，不应替代关键路径验证。

## 验证清单

完成后检查：
1. 已定位测试文件或明确说明缺失
2. 已识别测试框架或说明阻塞原因
3. 已输出测试统计
4. 已输出失败详情与改进建议
5. 已生成或更新测试报告路径
