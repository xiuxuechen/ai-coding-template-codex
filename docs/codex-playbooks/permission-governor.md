# 执行权限治理 Playbook

## 目标

为 Codex 设计一套可执行的分级授权策略，在减少低风险高频确认的同时，保留对高风险操作的人工把关。

这个 playbook 保留 `/permission-governor` 的核心能力：
- 识别高频打断来源
- 区分开发、测试、数据库、网络和 destructive 场景
- 用分级模型输出授权建议
- 优先收敛为脚本白名单或窄前缀授权
- 与项目级 `07_EXECUTION_PERMISSION_POLICY.md` 对齐

## 输入

- 权限优化目标：必填，例如“减少频繁确认”
- 关注场景：可选，例如开发启动、测试、数据库写入
- 当前项目是否已有 policy：可选

## 输出

至少产出：
- 权限分级建议
- 场景分类结果
- 推荐授权方式
- 建议的脚本白名单或前缀白名单
- 不应自动放权的动作清单

## 依赖

- 相关 skill：`permission-governor`
- 相关模板：`CC_COLLABORATION/03_templates/00_foundation/_planning/07_EXECUTION_PERMISSION_POLICY.md`
- 上游文档：`Codex.md`

## 执行步骤

### 1. 检查是否已有项目级 policy

如果存在：
- 优先读取 `docs/_foundation/_planning/07_EXECUTION_PERMISSION_POLICY.md`
- 基于现有 policy 补充或修正建议

如果不存在：
- 先使用默认分级模型给建议
- 如用户希望落地，再创建或补齐 policy 文档

### 2. 识别高频场景

重点关注：
- 本地开发启动
- 本地测试执行
- 数据库测试数据写入
- destructive 数据库操作
- Git 写操作
- 网络与依赖安装

### 3. 按三维模型分类

分类维度：
- environment
- action
- entry

要求：
- 环境必须区分本地、共享环境、staging、production
- 入口必须区分项目脚本和通用解释器或客户端

### 4. 给出分级授权建议

建议默认使用：
- `A`：默认放行
- `B`：允许可复用前缀授权
- `C`：逐次确认
- `D`：强确认，不做持久放权

### 5. 优先建议脚本白名单

原则：
- 优先让项目提供固定脚本
- 再对白名单脚本申请窄前缀授权
- 不直接对白名单 `mvn`、`mysql`、`bash`、`python`

### 6. 输出项目级建议

至少说明：
- 哪些动作适合自动化
- 哪些动作适合前缀授权
- 哪些动作必须逐次确认
- 哪些动作必须强确认

## 核心原则

1. 提升效率的重点是低风险高频动作，而不是无限放权。
2. 越危险的动作，授权越具体、越短期、越不可复用。
3. 项目脚本比通用命令更适合作为授权入口。
4. 本地开发与生产环境必须严格区分。

## 文档要求

- 主要内容使用中文
- `prefix_rule`、`policy`、`local-dev`、`staging` 等术语可保留英文

## 验证清单

完成后检查：
1. 已识别当前是否存在项目级 policy
2. 已对关键场景完成分类
3. 已给出分级授权建议
4. 已明确脚本白名单优先策略
5. 已明确不应自动放权的动作
