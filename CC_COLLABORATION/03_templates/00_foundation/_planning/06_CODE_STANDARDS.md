## 1. 文档定位

本文档是项目级代码规范的单一事实源，用于统一 AI 与人工协作时的实现约束、评审标准和测试要求。

适用范围：
- 所有 feature 的设计、编码、重构、测试与 review
- 所有 AI 生成代码、补丁、示例与修复建议

优先级规则：
1. 仓库根级强约束
2. 本文档 `docs/_foundation/_planning/06_CODE_STANDARDS.md`
3. 项目已有规范文档与目录约束
4. feature 级补充约束
5. 语言或框架默认最佳实践

约束说明：
- feature 文档可以增加更严格规则，但不应与本规范冲突
- 如需偏离本规范，必须在 `05_TECH_DECISIONS.md` 中记录原因
- 如项目已有更细的落地规范，应将其作为本文件的补充来源，而不是平行来源

## 2. 通用原则

### 2.1 变更原则

- 优先做最小必要改动，避免顺手重构无关代码
- 优先保持现有行为稳定，再考虑结构优化
- 不改原有业务语义，不做无关重构
- 新代码必须与仓库既有风格、分层、命名和对象模型保持一致
- 未确认收益前，不引入额外抽象层、第二套模式或第二套路由风格
- 不允许为了“统一风格”批量改名存量类、包、路径
- 历史拼写问题或旧路径默认保持兼容，不顺手修正
- 修复问题时优先补齐验证，而不是只改表面现象

### 2.2 可读性原则

- 命名优先表达业务含义，避免模糊缩写
- 函数、文件和模块职责应保持清晰
- 复杂逻辑需要拆分或加简短注释说明意图
- 注释解释“为什么”，不要解释显而易见的“做了什么”
- 新增方法优先提前返回，降低嵌套层级
- 新增或重构的方法原则上控制在 `50` 行左右；只在当前需求范围内拆分存量长方法
- 生成的新方法必须补中文 JavaDoc 注释
- 类中的任何 `private` 级别方法都必须补完整的 JavaDoc 注释，至少说明方法作用、参数含义、返回值和必要的前置条件
- 主动清理无用 import、无用变量、重复逻辑和明显重复判断

### 2.3 一致性原则

- 优先复用已有模式、目录约定和工具链
- 同类问题在不同模块中应采用一致写法
- 避免在同一仓库中混用多套风格与范式
- 如项目存在领域前缀体系，应优先沿用，而不是新造一套命名方式

- ORM 相关实现必须遵循项目已有封装，不随意绕过基础基类或统一访问层

## 5. 分层与目录规范

### 5.1 模块职责

| 模块 | 职责 |
|------|------|
| `web` / `api` 层 | Controller 入口层 |
| `service` 层 | 业务实现层 |
| `common` / `domain` 层 | 实体、Mapper、共享模型、工具类 |
| `facade` / `client` 层 | 外部调用门面与降级处理 |

### 5.2 包与目录规范

- Controller：`{base-package}.controller.<terminal>.<biz>`
- Service 接口：`{base-package}.service.modules.<terminal>.<biz>`
- Service 实现：对应 `impl` 子包
- Common：`entity`、`mapper`、`model`、`utils`、`enums`、`constant`
- Mapper XML：`resources/mapper/<biz>/`
- Facade：`{base-package}.facade`
- Fallback Factory：`{base-package}.facade.factory`

### 5.3 严禁事项

- `controller` 中写核心业务编排
- `service` 中直接承担页面返回包装职责
- `mapper` 中写业务流程编排
- `facade` / `client` 中放真实业务实现

### 5.4 跨层边界补充

- `controller` 只负责参数接收、权限控制、返回封装
- `service` 负责业务编排、事务、状态流转和领域规则
- `mapper` 负责数据访问，不承载业务决策
- `facade` / `client` 负责远程调用协议，不放业务实现逻辑

## 6. 接口与命名规范

### 6.1 接口路径规范

接口路径统一采用“端前缀 + 业务 + 具体能力”的结构。

常见前缀示例：
- 管理端前缀：`/manage-admin`
- 商家端前缀：`/merchant-admin`
- App 前缀：`/app`
- 内部远程接口：`/inner` 或项目定义的统一内部前缀

约束：
- 路径命名统一使用横杠，不使用驼峰
- 驼峰转横杠示例：`blackList` -> `black-list`
- 新增接口时必须先与现有模块路径风格保持一致

### 6.2 方法命名规范

| 场景 | 方法名 |
|------|--------|
| 分页查询 | `queryPageList` |
| 列表查询 | `queryList` |
| 单个查询 | `queryById` |
| 保存 | `save` |
| 修改 | `updateById` |
| 删除 | `deleteById` / `deleteByIds` |
| 校验 | `checkXX` |
| 填充 | `fillXX` |
| 批量状态变更 | `batchUpdateStatus` |

约束：
- 禁止随意发明同义方法名，例如 `getPage`、`listPage`、`modify`
- 同类能力在 Controller、Service、Mapper 三层的命名应尽量对齐

### 6.3 数据对象规范

| 类型 | 用途 | 命名规范 |
|------|------|----------|
| DTO | 入参对象 | `XxxListDto`、`XxxQueryDto` |
| VO | 出参对象 | `XxxListVo`、`XxxDetailVo` |
| BO | 业务对象 | `XxxSaveBo`、`XxxUpdateBo` |
| Entity | 实体对象 | 与数据库表一一对应 |

约束：
- DTO 只承载请求参数，不混入数据库实体语义
- VO 只承载返回结构，不直接暴露内部 Entity
- BO 用于承接业务编排，不直接替代 DTO 或 Entity
- 当接口或方法入参只有一个字段且语义清晰时，不强制创建 DTO / VO 类，可直接使用单个参数承接
- DTO / VO / BO 中的每个字段都必须补充字段级 JavaDoc 注释，不允许省略
- 枚举类字段、状态类字段、类型类字段的注释中必须明确取值映射，例如：`是否查询：0-否，1-是`

### 6.4 补充命名约束

- Service 接口统一使用 `I` 前缀
- Service 实现统一使用 `xxxServiceImpl`
- 列表字段优先使用 `xxList`
- 状态字段优先使用 `xxStatus`
- 类型字段优先使用 `xxType`
- JSON 配置字段优先使用 `xxConfig`

### 6.5 Restful 规范

- `@GetMapping`：查询、获取信息
- `@PostMapping`：保存
- `@PutMapping`：修改
- `@DeleteMapping`：删除

补充：
- 特殊批量查询在参数过长时，可使用 `POST`
- 但必须在命名和注释中明确这是查询语义，不要伪装成写操作

## 7. Controller 规范

- 返回统一使用项目约定的响应包装，例如 `R<T>` 或分页包装对象
- 需要权限控制的后台接口优先使用 `@PreAuthorize`
- 写接口优先评估是否需要 `@PreventRepeatSubmit`
- 入口参数优先使用 `@Validated` 与分组校验
- 后台或开放写接口默认评估是否需要变更日志注解，例如 `@ApiChangeLog`
- Controller 只负责参数接收、权限控制、返回封装，不写复杂业务流程

---

## 8. Service 规范

- Service 负责业务编排、事务、状态流转和领域规则
- 方法体原则上不超过 `50` 行；过长逻辑需拆分
- 优先提前返回，避免深层嵌套
- 批量查询后统一组装，避免明显 `N+1`
- 复杂规则应抽离为独立领域服务或策略实现，避免单类膨胀
- 不在 Service 中直接调用原始数据库工具快捷入口，例如 `Db.xxx`
- 涉及主子表保存、批量处理、状态流转时，必须明确事务边界
- 优先使用 `@Transactional` 或项目现有事务模板
- 涉及多租户数据时，默认补齐租户上下文和条件约束
- 同一个类中当方法 `a` 调用方法 `b` 时，如 `b` 是当前类实例方法，必须显式使用 `this.b(...)` 调用
- 禁止过度封装没有业务语义的薄方法，例如单纯做字符串 `trim`、单纯从 `List` 中提取某个字段形成新 `List` 这类可被直接表达的操作

---

## 9. Mapper 与数据访问规范

### 9.1 Mapper 调用规范

- `ServiceImpl` 中的 Mapper 实例优先统一命名为 `baseMapper`
- 必须遵循项目已有的基础 Mapper 封装
- 涉及多数据源时，遵循项目动态数据源约定
- 某张表或某个领域的数据访问，优先沉淀到自己的 Mapper
- 当前 Mapper 缺方法时，在当前 Mapper 和对应 XML 中补，不跳去别的 Mapper 复用不相干方法
- Service 不要绕过边界直接访问其他领域 Mapper

### 9.2 SQL 约束

- 禁止超过 2 个表的复杂联表成为默认方案
- 避免复杂 SQL，优先通过冗余字段、分步查询或批量组装解决复杂查询
- 避免在业务高频路径中编写难维护的嵌套 SQL
- SQL 可读性必须优先，必要时拆分为多步查询
- 查询数据库时，如果实际只需要 `5` 个字段以内，则不要默认全量查询，应优先只查业务真正需要的字段；但查询涉及 JSON 字段时可例外，因为 MyBatis-Plus 的 Wrapper 场景下通常不便同时安全指定 `select`，另外当该表本身总字段数就很少时，也允许直接查询全量字段
- XML 参数应使用 `@Param` 明确声明
- XML 语句命名必须表达业务语义，禁止 `selectList1`、`selectData2` 这类命名
- 默认值初始化放业务代码，不依赖数据库默认值完成业务初始化

### 9.3 数据访问性能约束

- 禁止出现明显的 `N+1` 查询
- 能批量查询时，不逐条查询
- 列表页和批处理接口必须优先关注查询次数与索引命中
- 修改数据访问逻辑时，同时检查租户条件、状态条件和索引命中风险

## 10. 集成与外部调用规范

- Feign / Client 接口统一放在门面模块
- 新增远程客户端必须配置降级处理，例如 `fallbackFactory`
- 新增内部远程 Controller 应统一放在远程入口目录，路径沿用项目约定的内部前缀
- 修改远程调用时，同步检查门面、远程 Controller、降级工厂以及相关自动装配配置
- 远程调用方法优先使用与现有项目一致的 HTTP 动词和封装风格
- 门面模块尽量不加新依赖，不放业务实现逻辑

## 11. 错误处理、校验与字段约束

### 11.1 错误处理

- 所有可预期失败路径必须有明确处理策略
- 错误信息应可定位问题，但不要泄露敏感信息
- 日志要记录关键上下文，不输出噪声或敏感字段
- 面向用户的报错文案与面向开发的日志应分离

### 11.2 校验规范

- 重复校验必须存在，即业务校验 + 数据库校验
- 字段长度必须严格限制，并且前后端都要校验
- 关键唯一性、状态合法性、引用合法性必须有后端兜底校验
- 不允许只依赖前端校验或只依赖数据库异常兜底
- 接口入参中“不能为空”“不能为 null”“长度限制”这类基础校验，优先使用 `org.springframework.validation` / `javax.validation` 体系的标准注解完成，不要在业务代码中用 `if` 做重复基础判断
- 参数对象优先使用 `@NotNull`、`@NotBlank`、`@NotEmpty`
- 新增/修改接口优先使用校验分组，例如 `AddGroup`、`EditGroup`
- 空字段判断、重复判断是否需要添加，必须基于业务规则、上下文语义以及表结构字段是否允许为空综合决定；禁止脱离业务语义和字段约束进行过度判空、过度判重

### 11.3 字段与输入约束

- 所有字符串字段都应有明确长度边界
- 列表查询条件要控制空值、默认值和边界值
- 导入导出场景必须对空值、非法值、超长值做保护

### 11.4 多租户补充规则

- 查询商户、配置、订单、设备等数据时，默认补齐 `tenantId`
- 涉及默认租户时，明确使用现有常量，而不是硬编码散落实现
- 初始化或复制租户数据时，明确创建人、租户 ID、默认状态
- 不允许把默认租户数据当普通租户数据直接修改

## 12. 测试与验证

### 12.1 基本要求

- 任何非纯文档改动都应说明验证方式
- 即使父工程默认跳过测试，改动后也必须做最小必要验证
- 修复 bug 时，优先补回归验证
- 涉及关键路径、边界条件、权限逻辑时必须补测试
- 未运行测试时，必须明确说明未验证项和风险

### 12.2 测试覆盖重点

- 正常流程
- 错误流程
- 边界条件
- 权限与安全相关场景
- 批量查询、批量导入导出场景
- 与外部依赖交互的降级场景

## 13. Review 约束

Review 时至少检查：
- 是否符合 Java 8 与当前技术栈约束
- 是否遵守接口路径、方法命名、DTO/VO/BO/Entity 规范
- 是否遵守基础 Mapper 封装、动态数据源与统一事务边界约定
- 是否存在超过约束的 SQL 复杂度、`N+1` 问题或方法体过长问题
- 是否缺少错误处理、边界处理、测试验证
- 是否引入了未说明的行为变化

## 14. Git 提交规范

- 默认使用中文提交信息
- 提交信息应优先概括“改动类型 + 改动对象 + 改动目的”，避免空泛描述
- 推荐格式：`type(scope): 中文说明`
- 常见 `type`：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`
- 如无特殊约束，不使用英文作为默认提交信息语言
- 如需改写已推送提交历史，必须先明确提醒存在 `amend` / `force-with-lease` 风险

## 15. AI 执行约束

### 15.1 执行边界

- 生成代码前先参考本规范和仓库现有代码风格
- 必须优先检查是否兼容 Java 8，禁止输出 Java 9+ 语法
- 必须优先遵循项目已有类命名、接口路径和对象分层习惯
- 不得仅因“看起来更现代”而大范围改写已有实现
- 不得绕过现有 lint、test、目录与命名约定
- 输出修复建议时，优先给出最小可落地方案
- 当本规范与现有实现冲突时，先指出冲突，再决定是沿用旧模式还是推动规范升级
- 一次改动尽量只解决一个业务问题
- 不顺手修无关问题，除非它已经阻塞当前需求
- 新增接口时，同步检查 Controller、Service、DTO/BO/VO、Mapper/XML、权限与日志注解
- 修改远程调用时，同步检查 Remote Controller、Facade、Fallback Factory、自动装配配置
- 修改 Mapper 逻辑时，优先补当前 Mapper 方法，不跳到其他 Mapper

### 15.2 AI 自检清单

- 是否遵守当前模块分层
- 是否沿用当前业务域命名和写法
- 新增方法是否补中文 JavaDoc
- Controller 返回是否符合仓库规范
- 查询是否补齐租户条件
- 是否存在明显 `N+1`
- 是否复用了现有工具类
- SQL 是否放在正确的 Mapper / XML
- 是否违反当前 Mapper 边界
- 写接口是否评估校验、权限、重复提交控制
- 是否做了最小必要验证
