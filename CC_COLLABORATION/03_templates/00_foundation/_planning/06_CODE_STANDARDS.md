## 1. 文档定位

本文档是项目级代码规范的单一事实源，用于统一 AI 与人工协作时的实现约束、评审标准和测试要求。

适用范围：
- 所有 feature 的设计、编码、重构、测试与 review
- 所有 AI 生成代码、补丁、示例与修复建议

优先级规则：
1. 仓库根级强约束
2. 本文档 `docs/_foundation/_planning/06_CODE_STANDARDS.md`
3. 项目已有规范文档与目录约束
4. feature 级补充约束
5. 语言或框架默认最佳实践

约束说明：
- feature 文档可以增加更严格规则，但不应与本规范冲突
- 如需偏离本规范，必须在 `05_TECH_DECISIONS.md` 中记录原因
- 如项目已有更细的落地规范，应将其作为本文件的补充来源而不是平行来源

## 2. 通用原则

### 2.1 变更原则

- 优先做最小必要改动，避免顺手重构无关代码
- 优先保持现有行为稳定，再考虑结构优化
- 新代码必须与仓库既有风格保持一致
- 未确认收益前，不引入额外抽象层
- 修复问题时优先补齐验证，而不是只改表面现象

### 2.2 可读性原则

- 命名优先表达业务含义，避免模糊缩写
- 函数、文件和模块职责应保持清晰
- 复杂逻辑需要拆分或加简短注释说明意图
- 注释解释“为什么”，不要解释显而易见的“做了什么”

### 2.3 一致性原则

- 优先复用已有模式、目录约定和工具链
- 同类问题在不同模块中应采用一致写法
- 避免在同一仓库中混用多套风格与范式

## 4. 技术栈

| 技术 | 版本 | 说明 |
|------|------|------|
| Java | 1.8 | 禁止使用 Java 9+ 语法 |
| Spring Boot | 2.7.18 | 作为应用启动和配置基础 |
| Spring Framework | 5.3.33 | 与 Spring Boot 2.7.x 对齐 |
| Spring Cloud | 2021.0.8 | 微服务基础能力 |
| Spring Cloud Alibaba | 2021.0.5.0 | 注册发现、配置、限流等扩展 |
| MyBatis-Plus | `jm-common-mybatis:2.0.20260211` | 使用 `BaseMapperPlus` 和动态数据源 |
| EasyExcel | 3.3.3 | 用于批量导入与导出 Excel |
| Lombok | 1.18.34 | 可使用 `@Data`、`@RequiredArgsConstructor` 等 |
| MySQL Connector | 8.0.33 | MySQL 驱动 |

### 4.1 Java 8 编码约束

- 禁止使用 `var`
- 禁止使用 `record`
- 禁止使用 text block `\"\"\"`
- 禁止使用 switch 表达式
- 禁止使用 `instanceof` 模式匹配
- 日期时间优先使用 `LocalDateTime`
- 集合处理允许使用 Stream API

### 4.2 技术栈落地原则

- 所有代码实现必须兼容 Java 8 编译与运行环境
- 代码示例、工具类、测试代码同样不得引入 Java 9+ 语法
- 依赖选型和 API 用法应与 Spring Boot 2.7.x 体系保持一致
- MyBatis-Plus 相关实现必须遵循项目已有封装，不绕开 `BaseMapperPlus`

## 5. 接口与命名规范

### 5.1 接口路径规范

接口路径统一采用“端前缀 + 业务 + 具体业务”的结构。

- 管理端前缀：`/manage-admin`
- 商家端前缀：`/merchant-admin`

示例：
- `/manage-admin/black-list/list`
- `/merchant-admin/black-list/list`

约束：
- 路径命名统一使用横杠，不使用驼峰
- 驼峰转横杠示例：`blackList` -> `black-list`
- 新增接口时必须先与现有模块路径风格保持一致

### 5.2 方法命名规范

| 场景 | 方法名 |
|------|--------|
| 分页查询 | `queryPageList` |
| 列表查询 | `queryList` |
| 单个查询 | `queryById` |
| 保存 | `save` |
| 修改 | `updateById` |
| 删除 | `deleteById` |
| 校验 | `checkXX` |
| 填充 | `fillXX` |

约束：
- 禁止随意发明同义方法名，如 `getPage`, `listPage`, `modify`
- 同类能力在 Controller、Service、Mapper 三层的命名应尽量对齐

### 5.3 数据对象规范

| 类型 | 用途 | 命名规范 |
|------|------|----------|
| DTO | 入参对象 | `XxxListDto` 等 |
| VO | 出参对象 | `XxxListVo`、`XxxDetailVo` |
| BO | 业务对象 | 保存、修改场景使用 |
| Entity | 实体对象 | 与数据库表一一对应 |

约束：
- DTO 只承载请求参数，不混入数据库实体语义
- VO 只承载返回结构，不直接暴露内部 Entity
- BO 用于承接业务编排，不直接替代 DTO 或 Entity

### 5.4 Restful 规范

- `@GetMapping`：查询、获取信息
- `@PostMapping`：保存
- `@PutMapping`：修改
- `@DeleteMapping`：删除

补充：
- 特殊批量查询在参数过长时，可使用 `POST`
- 但必须在命名和注释中明确这是查询语义，不要伪装成写操作

## 6. Mapper 与数据访问规范

### 6.1 Mapper 调用规范

- `ServiceImpl` 中的 Mapper 实例必须命名为 `baseMapper`
- 使用重新定义的内置方法，例如 `baseMapper.save()`、`baseMapper.queryById()`
- 必须遵循项目已有的 `BaseMapperPlus` 封装
- 涉及多数据源时，遵循项目动态数据源约定

### 6.2 SQL 约束

- 禁止超过 2 个表的表连接
- 避免复杂 SQL，优先通过冗余字段解决复杂查询
- 避免在业务高频路径中编写难维护的嵌套 SQL
- SQL 可读性必须优先，必要时拆分为多步查询

### 6.3 数据访问性能约束

- 禁止出现明显的 N+1 查询
- 能批量查询时，不逐条查询
- 列表页和批处理接口必须优先关注查询次数与索引命中

## 7. 业务层实现规范

- 遵循单一职责原则
- 方法体原则上不超过 50 行
- 优先使用提前返回，避免深层嵌套
- 避免过长判断分支，必要时使用策略模式
- 处理所有 warning，包括重复代码、无用变量、无意义分支等
- 常量优先使用枚举类表达，避免散落的静态常量

补充要求：
- Controller 负责参数接收与结果返回，不承载复杂业务
- Service 负责业务编排，不直接塞入大量 SQL 细节
- 复杂规则应抽离为独立领域服务或策略实现，避免单类膨胀

## 8. 错误处理、校验与字段约束

### 8.1 错误处理

- 所有可预期失败路径必须有明确处理策略
- 错误信息应可定位问题，但不要泄露敏感信息
- 日志要记录关键上下文，不输出噪声或敏感字段
- 面向用户的报错文案与面向开发的日志应分离

### 8.2 校验规范

- 重复校验必须存在，即业务校验 + 数据库校验
- 字段长度必须严格限制，并且前后端都要校验
- 关键唯一性、状态合法性、引用合法性必须有后端兜底校验
- 不允许只依赖前端校验或只依赖数据库异常兜底

### 8.3 字段与输入约束

- 所有字符串字段都应有明确长度边界
- 列表查询条件要控制空值、默认值和边界值
- 导入导出场景必须对空值、非法值、超长值做保护

## 9. 测试与验证

### 9.1 基本要求

- 任何非纯文档改动都应说明验证方式
- 修复 bug 时，优先补回归验证
- 涉及关键路径、边界条件、权限逻辑时必须补测试
- 未运行测试时，必须明确说明未验证项和风险

### 9.2 测试覆盖重点

- 正常流程
- 错误流程
- 边界条件
- 权限与安全相关场景
- 批量查询、批量导入导出场景
- 与外部依赖交互的降级场景

## 10. Review 约束

Review 时至少检查：
- 是否符合 Java 8 和当前 Spring 版本约束
- 是否遵守接口路径、方法命名、DTO/VO/BO/Entity 规范
- 是否遵守 `baseMapper`、`BaseMapperPlus`、动态数据源约定
- 是否存在超过约束的 SQL 复杂度、N+1 问题或方法体过长问题
- 是否缺少错误处理、边界处理、测试验证
- 是否引入了未说明的行为变化

---

## 11. AI 执行约束

当使用 AI 协作编码时，默认要求：
- 生成代码前先参考本规范和现有代码风格
- 必须优先检查是否兼容 Java 8，禁止输出 Java 9+ 语法
- 必须优先遵循项目已有类命名、接口路径和对象分层习惯
- 不得仅因“看起来更现代”而大范围改写已有实现
- 不得绕过现有 lint、test、目录与命名约定
- 输出修复建议时，优先给出最小可落地方案
- 当本规范与现有实现冲突时，先指出冲突，再决定是沿用旧模式还是推动规范升级
