# Release


## 参数

- `$ARGUMENTS`：格式为 `{feature-name} {version}`
  - feature-name：功能模块名称
  - version：版本号（如 `v1.0.0`、`1.0.0`）

## 执行步骤

### 1. 验证参数

解析参数，提取功能名称和版本号：
```
输入：user-auth v1.0.0
功能：user-auth
版本：v1.0.0
```

如果参数不完整，提示：
```
请提供完整参数，例如：/release user-auth v1.0.0

参数说明：
• feature-name: 功能模块名称
• version: 版本号（推荐使用语义化版本，如 v1.0.0）
```

### 2. 收集发布信息

读取以下文件收集信息：
- `docs/{feature-name}/10_CONTEXT.md` - 功能描述
- `docs/{feature-name}/90_PROGRESS_LOG.yaml` - 完成的任务
- `docs/{feature-name}/40_TEST_REPORT.md` - 测试结果（如有）
- `docs/{feature-name}/91_DAILY_SUMMARY/` - 历史工作记录

### 3. 验证发布条件

检查是否满足发布条件：
- [ ] Phase 5 Code 阶段已完成
- [ ] Phase 6 Test 阶段已完成（或跳过）
- [ ] 没有进行中的任务
- [ ] 没有阻塞的问题

如果不满足，提示：
```
⚠️ 发布检查未通过

问题：
• {issue_1}
• {issue_2}

请解决以上问题后再执行发布。
```

### 5. 创建 Git Tag（可选）

如果用户确认，创建 Git tag：

```bash
git tag -a {feature-name}-{version} -m "Release {feature-name} {version}"
```

### 6. 更新进度日志

更新 `90_PROGRESS_LOG.yaml`：
- 将 Phase 7 Deploy 阶段标记为 done
- 更新 `meta.status` 为 `released`
- 添加 release 信息

```yaml

  version: "{version}"
  released_at: "{current_datetime}"
  release_notes: "docs/{feature-name}/70_RELEASE_NOTES/{version}.md"
```

## 版本号规范

推荐使用语义化版本（Semantic Versioning）：
- **MAJOR.MINOR.PATCH**（如 1.0.0）
- MAJOR：不兼容的 API 修改
- MINOR：向下兼容的功能性新增
- PATCH：向下兼容的问题修正

版本号前缀 `v` 可选（`v1.0.0` 等同于 `1.0.0`）

## 注意事项

- 发布前必须完成测试阶段
- Release Notes 会自动汇总所有完成的任务
- Git tag 创建是可选的，需要用户确认
- 发布后功能状态变为 released
- 支持预发布版本（如 `v1.0.0-beta.1`）
